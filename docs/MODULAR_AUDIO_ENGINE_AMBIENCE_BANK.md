# Credit-prepared stereo ambience banks

Status: standalone live-context profile, not normal Ambience adoption. Thirteen focused checks and the five-case actual desktop browser startup/swap/cancellation/replay gate pass. The accepted immutable ambience reader and existing defaults are unchanged.

## Source and resource contract

This profile retains the original wind/fire/vinyl Rust preparation and complete 29/23/18-second stereo resources. The paged reader implements the accepted native BufferSource cursor law, including fractional onset, offset rounding, interpolation across page/loop boundaries, absolute stop, independent pulled age and reused-context HostRenderClock. It adds no playback worker delay, rate conversion, analytic waveform or source trimming. Existing host gain crossfades, spatial processing, shelter, weather and level wander remain separate.

A context owns one arena with sixteen metadata slots and sixteen independent stereo source cursors. Arena pages contain 1024 frames from each channel. Capacity is ceil(169 * sampleRate / 1024) + 16 pages: enough for the six actual old/new loops (140 seconds), one largest replacement (29 seconds), and page rounding. Reservation preflights all required pages before changing state. An eighth largest overlapping reservation refuses atomically; existing banks and cursors remain usable. Monotonic bank keys, worker generations and source slot tokens reject stale operations.

The PCM arena is bounded by 256 MiB, at integer rates 8k through 192k. Measured private Wasm instances at 8/44.1/48/88.2/96/192k use 10,952,704 / 59,760,640 / 65,028,096 / 119,382,016 / 129,925,120 / 259,719,168 arena bytes. The 192k full Wasm memory occupies 261,357,568 bytes including tables/stack/allocator overhead. Those values exclude worker preparation/readback arrays, browser PCM, transferred buffers and other instruments; total phone/process headroom is not established. Local desktop cold allocation took about 2–45 ms across those rates and must not run while output is active.

## Preparation and publication

A direct MessagePort connects the original Rust preparation worker to the pool receiver. PCM never passes through the main-thread controller. The worker owns two reusable stereo packets of at most 16,384 frames each (128 KiB each); at most two packets are outstanding. Each hot callback consumes at most one 1024-frame stereo slice. The receiver validates finite samples and sequential offsets, writes one inactive page, then reads that stored page back into the same packet slice. Returned packets build a complete worker-owned receiver readback. Full channel SHA256 and the complete resource fingerprint must equal the original immutable prepared PCM before publication. Hashing and whole-resource scans run in the worker, not the audio callback. Final publication changes resource metadata only.

Thus each hot callback performs at most four bounded 8 KiB stereo copy loops (packet to scratch, scratch to page, page to scratch, scratch back to packet), plus a finite-value scan. Packet metadata, sixteen output buses and bounded page reclamation add separate work. No large final copy occurs. Retired pages return through a bounded 32-page reclamation step. Rust upload, source controls, render, cancellation, reclamation and reset allocate/free/grow zero after cold construction; this is verified with the separate allocation-audit Wasm. This claim does not assert that browser JS MessagePort dispatch or the engine's JS runtime allocate nothing.

Only verified inactive banks can acquire new source references. Source disposal releases its slot after acknowledgement, and old resource storage remains retained while a source uses it. At most eight active/queued preparation descriptors are accepted. Queue, resource or cursor exhaustion refuses before unrelated source mutation. Aborting a partial upload or replacing a worker generation does not alter active source PCM. True transport/processor failure closes the pool explicitly; no silent native fallback occurs.

## Suspended startup policy

`prepareAmbienceBankPool(context)` requires a suspended live AudioContext and rechecks that state after async loading. The worklet rejects cold arena creation after its first actual callback or after the captured suspended origin. Initial cold preparation drains one bounded slice per control-message pump, so it does not depend on `process()` while suspended. It never resumes the context implicitly.

Once any callback has run, all PCM upload slices run only inside callbacks. A suspended reused context refuses new uploads before reserving resources. The caller may explicitly invoke `pool.warmup({resume:true})` with its audible routes muted; active owned source demands must be disconnected/muted first. Other application routes must also be muted by the caller. The API does not fabricate a warmup by resuming an unrequested user context. Cold startup timeout produces a bounded explicit error rather than waiting forever; an explicit muted warmup can allow a platform that defers construction until resume. The arena must still precede the first active callback.

OfflineAudioContext uses the accepted immutable owned reader for snapshots. The new live factory rejects an offline context explicitly. This is a separate executor policy, not a change to the prepared sound or a native fallback.

## Public adapter and persistence

`prepareAmbienceBankPool(context)` returns the context-bound pool. `pool.prepare(kind, shape, {signal})` or `pool.prepare(spec)` resolves a verified bank lease with complete immutable identity and publication metrics. The lease owns one reference; `release()` is idempotent. `pool.source(lease)` returns one source exposing creation-only `ready`, start/stop seconds, connect/disconnect, explicit host demand, onended, status, save and acknowledged dispose. A source retains its own bank reference. Each physical source has a distinct worklet output, preserving downstream native routing.

`pool.restore(json)` regenerates the exact original preparation resource, validates the full receiver fingerprint and preparation Wasm, then books the saved start/offset/stop setup. JSON captures immutable resource identity plus authored controls. It does not capture an in-flight cursor, active crossfade or executor setting. Unsupported rates, invalid metadata and incompatible preparation identity refuse explicitly.
