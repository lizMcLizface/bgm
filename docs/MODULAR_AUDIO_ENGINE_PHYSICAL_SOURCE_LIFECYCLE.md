# Physical source terminal ownership: Stage A

Stage A gives the shared owned piano/KS source controller an actual per-node terminal fence and makes both numerical preparation-worker pools own partial construction failures. It does not certify the wider Instrument/MonoSynth constructor, change Main admission, select a new default, or port any measured cello path. The separate legacy `pianoLiveSource` controller remains outside this typed-node upgrade; the prepared normal piano factory uses `pianoStreamingSource` over the shared physical controller.

Each shared physical controller owns one AudioWorkletNode and one full Rust Engine. Its per-voice hooks refer to slots in that engine and receive no separate disposal authority. `disposalStatus()` and `node.sourceDisposalStatus()` expose the same actual node's `source-terminal-receipt-v1` fence. `dispose()` now returns one idempotent Promise: it attempts preparation termination, restores only hooks it installed, detaches its private node edge, drains canceled preparation results and awaits the actual terminal receipt. A valid receipt follows the Rust handle free. A failed free reports a typed negative with `released:false`; post-free cleanup failure reports `released:true, clean:false`. Neither is silently accepted.

A missing acknowledgement rejects and quarantines ownership. The minimal receiver remains attached until a late real terminal receipt or actual context close. A timer does not prove release and does not close that receiver. Late release can update observed released state but cannot turn the already rejected retirement Promise into success. Deferred Offline construction has no physical node before its existing final preparation boundary, so its separate no-node status never pretends to certify a shared slot or an uncreated node.

Node construction, connection, initial controls and per-voice-hook setup now have failure-only cleanup. A constructor failure's `cleanupReady` is awaited before the async source factory rejects. Every acquired owner is attempted even if an earlier nested cleanup promise rejects; primary failures and cleanup errors remain distinct. No suspended/offline render-start health wait is added.

Each piano or KS preparation pool still owns at most two workers. Worker records are registered incrementally before handler setup. A second constructor, handler setup or post failure terminates every acquired worker and rejects queued/inflight work. Termination attempts continue after an earlier termination throws. `cleanupReady` records the result for an enclosing asynchronous factory; termination failure is retained as `cleanupError`. Healthy numerical requests, IDs, worker selection and original queue bounds are unchanged. The existing streaming piano adapter still bounds combined active/queued jobs to2000; the old standalone piano pool retains its separate2000-queued plus at most2-active bound.
